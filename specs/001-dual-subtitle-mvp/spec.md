## Clarifications

### Session 2026-05-27

- Q: 한↔일 번역의 어조/문체 정책은 무엇으로 하시겠습니까? → A: 원문 어조 보존 (정중체 ↔ 정중체, 친근체 ↔ 친근체)
- Q: 입력 영상의 길이 하드 상한을 어떻게 설정하시겠습니까? → A: 60분 초과 거절 (입력 시점에 INVALID_INPUT으로 반려) — *2026-05-28 후속 결정으로 120분으로 확장됨 (아래 참조)*
- Q: 작업 취소 시 부분 산출물은 어떻게 처리하시겠습니까? → A: 즉시 완전 삭제 (`var/storage/<job_id>/` 전체 제거, DB row는 `failed` / `USER_CANCELLED`로 유지)
- Q: 완료/실패 작업의 보존·자동 정리 정책을 어떻게 가져가시겠습니까? → A: 자동 정리 없음 — 사용자가 수동으로만 정리 (MVP는 단일 호스트·단일 사용자 전제)
- Q: 동시 처리 가능한 작업 수의 기본 상한은 몇 건으로 하시겠습니까? → A: 2건 (기본값, 환경변수 `JOB_CONCURRENCY`로 조정 가능)

### Session 2026-05-28

- Q: 영상 길이 하드 상한을 60분에서 더 늘려야 하는가? → A: **120분(7200초)으로 확장**. 강의·세미나·라이브 다이제스트 등 60~120분 콘텐츠 수요가 확인되어 상한을 두 배로 완화한다. 비용·처리 시간 예측은 [research.md §16.2](./research.md#162-영상-길이-하드-상한-120분)에서 재산정. SC-001 측정 기준(15분 영상 ≤ 10분)은 영향 없음.
- Q: 종결 작업(completed/failed)을 사용자가 목록에서 삭제할 수 있어야 하는가? → A: **가능. Hard delete 시맨틱.** 사용자가 목록의 종결 작업 카드에서 삭제를 명령하면 `var/storage/<job_id>/` 산출물과 DB `video_job` 행(및 cascade 관련 SubtitleTrack / Cue / Asset / JobEvent / TranslationTask / RenderTask)을 영구 제거한다. 진행 중 작업은 기존 cancel(`error_code=USER_CANCELLED`로 DB row 보존) 경로 그대로이며, 종결 후 별도 삭제 액션이 필요하다. spec L210의 "명시적 삭제 API 후속 확장에서 결정" 항목을 본 결정으로 종결한다.
- Q: 영상에 source/target 두 언어 자막이 모두 임베디드되어 yt-dlp 가 두 vtt 를 함께 다운로드하면, LLM 번역을 어떻게 처리하는가? → A: **번역 단계를 건너뛴다.** extract_subtitles 가 두 트랙(`kind="source"` + `kind="translated"`, `origin` 은 manual/auto 그대로)을 모두 DB 에 저장하고, translate_task 는 시작 시점에 translated 트랙이 이미 존재함을 감지하면 progress=1.0 publish 후 즉시 정상 종료한다. provider rate limit / 비용 회피 + 원본 임베디드 번역 품질 보존이 목적. FR-013a 로 명시.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 단일 영상으로 dual subtitle 시청 완료 (Priority: P1) 🎯 MVP

일본어 학습 중인 사용자가 좋아하는 일본어 YouTube 영상의 URL을 붙여넣고 처리 시작 버튼을 누른다. 잠시 기다린 뒤, 같은 화면에서 영상이 재생되며 화면 하단에 일본어 원문과 한국어 번역이 함께 표시된다. 사용자는 dual subtitle을 켜고 끄거나 표시 순서를 바꿀 수 있다.

**Why this priority**: 본 기능이 곧 MVP의 본질이다. 이 시나리오가 동작하지 않으면 제품 자체가 존재 의미를 잃는다. P2·P3 없이 P1만 구현되어도 사용자는 핵심 가치를 얻을 수 있다.

**Independent Test**: 자막이 존재하는 5~15분 길이의 일본어 YouTube 영상 URL 1건을 입력 → 처리 완료 → 브라우저에서 dual subtitle과 함께 재생되는지 확인. 한↔일 양방향 모두 동일하게 검증 가능.

**Acceptance Scenarios**:

1. **Given** 자막이 제공되는 일본어 YouTube 영상 URL, **When** 사용자가 URL을 입력하고 처리를 시작, **Then** 처리가 완료된 후 같은 영상이 브라우저에서 재생되고, 각 자막 구간에 일본어 원문과 한국어 번역이 함께 표시된다.
2. **Given** 자막이 제공되는 한국어 YouTube 영상 URL, **When** 사용자가 URL을 입력하고 처리를 시작, **Then** 한국어 원문 + 일본어 번역의 dual subtitle이 생성되어 재생된다.
3. **Given** dual subtitle이 표시된 재생 화면, **When** 사용자가 자막 토글을 끔, **Then** 자막이 즉시 사라진다. 다시 켜면 dual subtitle이 복원된다.
4. **Given** dual subtitle이 표시된 재생 화면, **When** 사용자가 언어 표시 순서를 바꿈 (원문↔번역문), **Then** 두 줄의 순서가 즉시 반대로 표시된다.
5. **Given** 수동 자막과 자동 자막이 모두 있는 영상, **When** 처리 시작, **Then** 수동 자막이 원문 소스로 사용된다.
6. **Given** 수동 자막이 없고 자동 자막만 있는 영상, **When** 처리 시작, **Then** 자동 자막이 원문 소스로 사용되며, 사용자는 자동 자막 사용 사실을 화면에서 인지할 수 있다.

### User Story 2 - 장기 작업 진행 상황 실시간 확인 (Priority: P2)

사용자가 처리를 시작한 직후, 같은 화면에서 어떤 단계가 진행 중인지(다운로드, 자막 추출, 번역, 렌더링 등) 실시간으로 볼 수 있다. 단계별 진행률 또는 단계 전이가 시각적으로 갱신되므로 사용자는 "멈춰 있는지" 의심하지 않는다.

**Why this priority**: 처리 시간이 분 단위로 길어질 수 있어, 가시성이 없으면 사용자는 새로고침하거나 같은 영상을 다시 요청해 시스템 부하를 키운다. P1 직후의 사용성 결정 요소.

**Independent Test**: 영상 처리 도중 작업 상세 페이지를 열어, 페이지를 새로고침하지 않아도 상태가 `pending → downloading → subtitle_processing → translating → rendering → completed` 순으로 갱신되는지 확인.

**Acceptance Scenarios**:

1. **Given** 처리 중인 작업의 상세 페이지가 열려 있음, **When** 단계 전이가 발생, **Then** 화면이 (페이지 수동 새로고침 없이) 새 상태를 일정 시간 내에 반영한다.
2. **Given** 처리 중인 작업, **When** 사용자가 다른 페이지로 이동했다가 돌아옴, **Then** 가장 최근 상태가 즉시 표시된다.
3. **Given** 어떤 단계에서 처리 실패, **When** 사용자가 상세 페이지를 봄, **Then** 실패 단계와 사용자 친화적 실패 사유 메시지가 표시된다.

---

### User Story 3 - 최근 작업 목록에서 재방문 (Priority: P3)

사용자는 메인 페이지에서 최근에 처리한 작업 목록을 보고, 그중 하나를 선택해 다시 재생할 수 있다. 동일한 URL을 다시 입력해 재처리하지 않아도 된다.

**Why this priority**: 재방문 가치 — 학습자는 같은 영상을 반복해서 보는 경우가 많다. 하지만 P1·P2가 완성되어야 의미가 있으므로 우선순위는 P3.

**Independent Test**: 영상 1건을 완료 처리한 뒤, 메인 페이지에서 해당 작업이 최근 목록에 나타나는지 확인하고, 클릭 시 dual subtitle 재생 화면이 즉시 열리는지 확인.

**Acceptance Scenarios**:

1. **Given** 1개 이상의 완료된 작업이 존재, **When** 사용자가 메인 페이지를 방문, **Then** 최근 작업 목록이 최신 순으로 표시되고 각 항목에는 최소한 영상 제목, 처리 상태, 처리 일시가 포함된다.
2. **Given** 최근 작업 목록의 완료 항목, **When** 사용자가 항목을 클릭, **Then** 해당 작업의 상세/재생 화면이 열리며 dual subtitle이 즉시 재생 가능하다.
3. **Given** 처리 실패 또는 진행 중인 항목이 목록에 포함, **When** 사용자가 항목을 클릭, **Then** 실패 사유 또는 진행 상태가 표시된다 (재생은 불가).

### Edge Cases

- **자막이 전혀 없는 영상**: MVP는 STT를 포함하지 않으므로 명확한 실패 메시지("자막을 찾을 수 없습니다 — 향후 음성 인식 지원 예정")와 함께 `failed` 상태로 종료한다.
- **원하지 않는 언어 자막만 존재**: ko/ja 외의 언어 자막만 있는 경우 MVP에서는 동일하게 실패 처리한다.
- **120분 초과 영상**: 메타데이터 추출 시점에 길이를 확인하여 작업 생성을 즉시 거절한다 (FR-003). 사용자에게 120분 제한과 향후 상한 확장 가능성을 안내한다.
- **동일 URL 재요청**: 이미 완료된 작업이 존재하면 신규 처리 없이 기존 결과를 재사용해 즉시 재생 가능 상태로 응답한다 (사용자는 "기존 결과로 이동"을 명시적으로 본다).
- **URL이 YouTube가 아니거나 유효하지 않음**: 입력 단계에서 즉시 거절하고, 작업 자체가 생성되지 않는다.
- **다운로드 / 번역 / 렌더링 중 어느 한 단계 실패**: 작업 상태가 `failed`로 전이되고, 실패 단계명과 사용자 친화적 사유가 노출된다. 부분 산출물(다운로드된 영상, 부분 번역 등)은 사용자에게 노출하지 않는다.
- **번역 provider rate limit 도달**: 재시도 정책 내에서 자동 재시도하고, 그래도 실패하면 명확한 실패 사유를 사용자에게 노출한다.
- **사용자가 처리 도중 동일 URL을 다시 제출**: 이미 진행 중인 작업이 있다면 신규 생성 없이 기존 작업의 상태로 안내한다.
- **자동 자막의 품질이 낮은 경우**: 원문 자막이 자동 자막임을 UI에서 명시한다 (사용자가 품질 한계를 인지할 수 있도록).

## Requirements *(mandatory)*

### Functional Requirements

#### URL 입력 & 메타데이터

- **FR-001**: 시스템은 단일 YouTube 영상 URL을 입력으로 받아 작업을 생성할 수 있어야 한다.
- **FR-002**: 시스템은 입력 URL이 YouTube 도메인의 단일 영상 URL인지 검증하고, 유효하지 않으면 즉시 거절해야 한다 (작업 미생성).
- **FR-003**: 시스템은 작업 생성 시점에 영상의 메타데이터(제목, 길이, 채널 등 표시 가능한 최소 정보)를 추출해 작업에 연결해야 한다. **영상 길이가 120분(7200초)을 초과하면 작업을 생성하지 않고 즉시 거절한다** (에러 코드 `INVALID_INPUT`, 사용자에게 120분 상한과 향후 확장 안내 메시지 노출).
- **FR-004**: 시스템은 동일 URL에 대한 완료 작업이 이미 있으면 신규 처리를 건너뛰고 기존 결과를 재사용해야 한다.

#### 영상 다운로드

- **FR-005**: 시스템은 mp4 우선, best available quality 기준으로 영상을 다운로드해야 한다.
- **FR-006**: 다운로드 실패에 대한 자동 재시도는 워커에서 처리해야 한다 (비동기·큐 의무는 FR-027의 적용). 재시도 정책 상세는 plan 단계에서 결정.
- **FR-007**: 다운로드 실패 시 시스템은 재시도 정책에 따라 자동 재시도하고, 최종 실패 시 작업 상태를 `failed`로 전이해야 한다.

#### 자막 추출

- **FR-008**: 시스템은 manual subtitle을 우선 사용하고, 없을 경우에만 auto subtitle을 fallback으로 사용해야 한다.
- **FR-009**: 시스템은 영상에 ko 또는 ja 자막이 있는지 자동으로 감지해 원문 언어를 결정해야 한다.
- **FR-010**: 시스템은 SRT 또는 VTT 형식의 자막을 정규화된 내부 형식으로 변환해야 한다.
- **FR-011**: ko/ja 자막이 모두 없는 경우 시스템은 작업을 `failed`로 종료하고 사유를 사용자 친화적으로 노출해야 한다.

#### 번역

- **FR-012**: 시스템은 한국어 → 일본어, 일본어 → 한국어 양방향 번역을 지원해야 한다.
- **FR-013**: 시스템은 자막을 chunk 단위로 분할해 번역해야 한다 (단일 호출에 전체 자막을 보내지 않음).
- **FR-013a** (2026-05-28 결정): 영상에 source / target 두 언어 자막이 모두 임베디드되어 yt-dlp 가 두 vtt 를 함께 다운로드한 경우, 시스템은 두 트랙을 모두 DB 에 등록(`kind="source"` + `kind="translated"`, `origin` 은 manual/auto 그대로)하고 번역 단계(LLM 호출) 를 건너뛰어야 한다. 이는 provider rate limit / 비용을 회피하고 사용자 영상의 원본 임베디드 번역 품질을 보존한다.
- **FR-014**: 시스템은 chunk 간 context를 보존해 번역 일관성을 유지해야 한다 (예: 인접 chunk의 문맥 정보 전달). **번역 출력의 어조/문체는 원문 어조를 보존해야 한다** — 원문이 정중체(KO: 합니다체 / JA: です·ます체)면 번역도 정중체, 친근체(KO: 한다체 / JA: だ·である체)면 친근체로 출력한다. cue 내부에서 어조가 혼재하면 다수 어조를 따른다.
- **FR-015**: 번역 호출 시 provider rate limit 도달이면 자동 재시도해야 한다 (비동기·큐 의무는 FR-027의 적용).
- **FR-016**: 번역 계층은 단일 provider에 결합되지 않는 추상화로 구현되어야 한다 (헌법 — Translation Provider Abstraction NON-NEGOTIABLE).

#### Dual Subtitle 생성

- **FR-017**: 시스템은 원문 자막과 번역 자막을 시간축에 정렬해 dual subtitle 산출물을 생성해야 한다.
- **FR-018**: 출력 형식은 SRT와 VTT 두 형식 모두 지원되어야 한다.
- **FR-019**: 각 자막 cue는 두 줄(원문 / 번역문) 또는 동등한 표현으로 구성되어 브라우저에서 두 언어가 함께 표시되도록 해야 한다.

#### 브라우저 재생

- **FR-020**: 시스템은 HTML5 video 재생기에서 영상을 재생할 수 있어야 한다.
- **FR-021**: 시스템은 dual subtitle을 영상 위에 overlay 형태로 표시해야 한다.
- **FR-021a**: 원문 자막의 출처가 자동 자막(yt-dlp `--write-auto-sub` fallback)인 경우, 재생 화면 메타데이터 영역에 자동 자막 사용 사실을 명시적으로 노출해야 한다 (예: "🤖 자동 자막 기반" 배지). 사용자는 자동 자막의 품질 한계를 인지할 수 있어야 한다. US1 acceptance 시나리오 6에 대응.
- **FR-022**: 사용자는 재생 화면에서 자막 표시를 토글할 수 있어야 한다.
- **FR-023**: 사용자는 두 언어의 표시 순서(원문 위/번역문 위)를 전환할 수 있어야 한다.

#### 작업 상태 추적 & 비동기 처리

- **FR-024**: 모든 작업은 다음 상태 중 하나를 가져야 한다 — `pending`, `downloading`, `subtitle_processing`, `translating`, `rendering`, `completed`, `failed`.
- **FR-025**: 상태 전이는 단방향이며 (`failed`는 어느 단계에서나 도달 가능), 동일 단계에서 재시도되는 동안 외부 관찰 상태가 갱신되어야 한다.
- **FR-026**: 사용자는 임의 시점에 작업 상태를 조회할 수 있어야 한다 (페이지 수동 새로고침 없이 실시간 갱신 가능해야 함).
- **FR-027**: 다운로드 / 자막 추출 / 번역 / 렌더링은 모두 비동기 워커에서 실행되어야 한다 (헌법 II — Queue-Based Processing NON-NEGOTIABLE). **시스템은 동시 처리 작업 수를 기본 2건으로 제한하며, 초과 작업은 `pending` 상태로 대기열에 보류된다**. 상한은 운영 시 환경변수(`JOB_CONCURRENCY`)로 조정 가능하다.
- **FR-028**: 워커 작업은 idempotent하고 retry 가능하며 cancellable해야 한다 (헌법). **취소가 확정되면 시스템은 해당 작업의 파일시스템 산출물(`var/storage/<job_id>/` 이하 일체)을 즉시 완전히 삭제한다.** DB의 `video_job` 행은 감사 목적으로 유지하되 상태를 `failed`, `error_code=USER_CANCELLED`로 기록한다.

#### 작업 이력

- **FR-029**: 시스템은 완료 / 진행 중 / 실패 작업의 목록을 최신 순으로 노출해야 한다.
- **FR-030**: 사용자는 목록에서 완료 작업을 선택해 즉시 재생 화면으로 진입할 수 있어야 한다.
- **FR-030a**: 사용자는 목록의 **종결 작업(completed/failed)** 을 영구 삭제할 수 있어야 한다. 삭제가 확정되면 시스템은 해당 작업의 파일시스템 산출물(`var/storage/<job_id>/` 이하 일체)과 DB `video_job` 행(및 cascade 관련 자산·트랙·큐·이벤트)을 영구 제거한다. 진행 중 작업은 본 동작 대상이 아니며 cancel(FR-028) 이후에만 삭제 가능하다. 삭제는 사용자 명시적 액션(목록 카드의 삭제 버튼 + 확인 다이얼로그)을 통해서만 발생하며, 자동 정리는 수행하지 않는다(Assumptions §데이터 보존 기간).

#### 보안 & 안전성

- **FR-031**: 시스템은 모든 사용자 입력 URL을 사용 전에 검증해야 한다.
- **FR-032**: 시스템은 사용자 입력에서 파생된 파일 경로를 sanitize해야 하며, path traversal을 허용해서는 안 된다.
- **FR-033**: 시스템은 미디어 도구 호출에 untrusted 문자열을 직접 interpolation해서는 안 된다 (shell command injection 방지).
- **FR-034**: 시스템은 시크릿을 코드에 하드코딩해서는 안 된다 (env 전용).
- **FR-035**: 시스템은 단위 시간당 작업 제출 횟수를 제한할 수 있어야 한다 (rate limiting).

#### 관찰 가능성

- **FR-036**: 시스템은 structured logging으로 단계 전이와 실패 사유를 기록해야 한다.
- **FR-037**: 시스템은 처리 중 발생한 에러를 작업과 연관 지어 추적할 수 있어야 한다.

#### 문서화

- **FR-038**: 본 저장소의 모든 마크다운 산출물(spec / plan / tasks / ADR / README)은 한국어로 작성되어야 한다 (헌법 V).

### Key Entities

- **VideoJob**: 사용자가 제출한 처리 작업 한 건. 상태(`pending`~`failed` 중 하나), 입력 URL, 영상 메타데이터, 처리 결과 산출물에 대한 참조, 생성/갱신 시각을 가진다. 모든 다른 엔티티의 부모.
- **SubtitleTrack**: 영상에 연결된 자막 트랙. 언어(ko/ja), 출처(manual/auto), 형식(SRT/VTT), 정규화된 cue 목록을 가진다. 원문 트랙과 번역 결과 트랙이 별개로 존재한다.
- **TranslationTask**: 단일 SubtitleTrack을 원문으로 하여 목표 언어로 번역하는 비동기 작업. chunk 분할 상태, 진행 chunk 인덱스, 재시도 횟수, provider 식별자를 가진다.
- **RenderTask**: 원문 + 번역문 SubtitleTrack을 합쳐 dual subtitle 산출물(SRT/VTT)을 만드는 비동기 작업. 출력 형식, 산출 파일 참조, 완료 여부를 가진다.

> **운영 보조 엔티티**: 위 4개 외에도 시스템 운영을 위한 보조 엔티티가 존재한다 — `SubtitleCue`(자막 트랙 내부 cue 데이터), `VideoAsset`(영상·자막·dual subtitle 파일 자산 참조), `JobEvent`(상태 전이·진행률 이벤트 영구화). 상세 스키마는 [data-model.md](./data-model.md)에서 정의한다.

#### Lifecycle / 상태 전이

`VideoJob`의 정상 경로:

```
pending → downloading → subtitle_processing → translating → rendering → completed
```

비정상 경로: 어느 단계에서나 `failed`로 전이 가능. `failed` / `completed`는 종결 상태로, MVP에서는 자동 재시작하지 않는다 (사용자는 새 작업을 생성해 재시도).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 자막이 제공되는 15분 길이의 일본어 영상을 입력했을 때, 사용자는 처리 시작부터 dual subtitle 재생까지 평균 10분 이내에 도달할 수 있다.
- **SC-002**: 처리 도중 사용자가 작업 상세 페이지에 머무는 경우, 단계 전이 발생 후 화면에 반영되기까지 평균 5초 이내이다.
- **SC-003**: 자막이 제공되는 정상 영상에 대해 end-to-end 성공률 ≥ 95% (네트워크/공급사 일시 장애 제외 기준).
- **SC-004**: dual subtitle의 시간축 정렬은 원문 자막의 cue 시점 대비 ±200ms 이내로 일치한다.
- **SC-005**: 동일 URL의 재요청 시 신규 처리 없이 기존 결과를 5초 이내에 사용자에게 노출한다.
- **SC-006**: 처음 사용하는 사용자가 추가 설명 없이 메인 페이지에서 URL을 입력해 dual subtitle 영상을 재생하기까지 도달할 수 있다 (1차 시도 성공률 ≥ 80%, 사용성 테스트 기준).
- **SC-007**: 새 작업 제출 API 응답은 동시 처리 한도(기본 2건) 도달 여부와 무관하게 1초 이내에 반환된다 (제출은 비동기이며, 초과 시 작업은 `pending`으로 큐에 들어간다).
- **SC-008**: 실패한 작업 100건 중 사용자 친화적 사유가 노출된 비율 100% (모든 실패는 단계명과 사유를 갖는다).

## Assumptions

- **자막 부재 영상은 MVP 스코프 외**: STT(예: Whisper)는 미래 확장이며 MVP는 자막이 있는 영상만 지원한다. 자막 없음은 명확한 실패로 처리한다.
- **단일 영상 1건 처리**: playlist 입력은 MVP 제외이며, URL은 단일 영상 형태만 허용한다.
- **인증 없음**: 로그인 / 회원 / 결제는 MVP 제외이므로, 작업은 단일 익명 사용자 컨텍스트에서 생성·조회된다. "최근 작업 목록"은 호스트 단위로 공유되는 단순 이력이다.
- **로컬 호스트 운영**: 클라우드 배포는 MVP 외이며, 본 사양은 macOS 로컬 호스트 실행을 전제로 한다 (헌법 IV).
- **번역 provider는 Claude Premium Seat**: 단, 사용자 가시 동작은 provider에 의존하지 않는다. provider 교체는 사용자 시나리오에 영향을 주지 않아야 한다 (헌법 — Translation Provider Abstraction).
- **영상 길이 하드 상한 = 120분**: 메타데이터 단계에서 초과 영상은 거절 (FR-003). SC-001 측정 기준(15분 영상 ≤ 10분)은 동일하게 유지된다.
- **재시도 정책 상세**: 횟수·backoff 등 구체 수치는 `/speckit-plan` 단계에서 결정 (본 사양은 "재시도가 존재한다"는 행위만 약속).
- **dual subtitle 스타일링 (폰트·색상·위치)**: MVP는 가독성 위주의 기본 스타일을 채택. 세부 스타일링은 추후 확장.
- **데이터 보존 기간**: MVP는 **자동 정리 없음**. 완료·실패 작업의 메타데이터(DB)와 산출물(`var/storage/`)은 사용자가 명시적으로 삭제할 때까지 무기한 보존된다. 사용자 수동 삭제는 종결 작업(completed/failed) 한정 hard delete로 제공한다(FR-030a, spec Clarifications 2026-05-28). 시간 기준·개수 기준 자동 정리는 후속 확장에서 결정한다.
- **기술·아키텍처 산출물 (백엔드 구조, API 스키마, DB 스키마, 미디어/번역 파이프라인 상세, 폴더 구조, 테스팅 매트릭스 등)** 은 `/speckit-plan` 단계에서 생성한다. 본 spec.md는 헌법 원칙 I·V에 맞게 WHAT/WHY에 한정한다.
